# Declarative Axum Router And Live LSP Plan

## Summary

The current API layer makes users repeat the same endpoint identity in several
places:

```rust
#[api_macros::api(method = "GET", path = "/greetings/{name}")]
async fn greet(name: Path<String>) -> Result<Json<Greeting>, GreetingError> {
    todo!()
}

pub fn api() -> ApiModule {
    api_module!(name = "server", endpoints = [greet])
}

pub fn app() -> Router {
    router(api())
        .route(__api_endpoint_greet(), greet_response)
        .into_router()
}

async fn greet_response(name: Path<String>) -> Response {
    api_axum::success_or_error(greet(name).await)
}
```

That shape works, but it gives the language server too many user-visible
references that are not normal Rust references:

- `api_module!(..., endpoints = [greet])`
- `__api_endpoint_greet()`
- `greet_response`
- `greet(name).await`
- `greetings.greet` in TypeScript

The better architecture is to make the axum router tree the export boundary.
Users should write the endpoint once, mount the real handler once, and let the
macro/runtime layer generate hidden adapters.

Target shape:

```rust
#[api_macros::api(method = "GET", path = "/greetings/{name}")]
pub async fn greet(name: Path<String>) -> Result<Json<Greeting>, GreetingError> {
    todo!()
}

#[api_macros::api_router]
pub fn routes() -> api_axum::ApiRouter {
    api_axum::ApiRouter::new("server")
        .endpoint(greet)
        .layer(TraceLayer::new_for_http())
}

pub fn app() -> axum::Router {
    routes().into_router()
}

pub fn contract() -> ApiContract {
    collect_contract(CollectorInput::from_root(TS_PACKAGE_NAME, routes()))
}
```

`#[api_router]` rewrites `.endpoint(greet)` to hidden descriptor and adapter
items generated by `#[api]`. The source graph and LSP index the original
`.endpoint(greet)` source, not generated helper names.

## Prior Art

The plan follows the shape used by other axum-adjacent projects:

- axum keeps composition in `Router` through `route`, `nest`, `merge`,
  `fallback`, `route_service`, `layer`, and `route_layer`.
- aide wraps `axum::Router` in `aide::axum::ApiRouter`, keeping runtime routes
  and OpenAPI metadata together.
- utoipa-axum wraps `axum::Router` in `OpenApiRouter`, and its `routes!` macro
  collects annotated handlers into a router plus metadata bundle.
- axum-autoroute annotates the real handler, detects extractors from the
  handler signature, and keeps public route metadata in a router wrapper.
- axum-extra typed routing shows that route registration can infer path
  metadata from handler-related types while preserving ordinary axum handlers
  and extractors.

The design here should preserve axum's composition model instead of replacing
it with a separate framework.

## Goals

1. Remove hand-written response wrapper functions like `greet_response`.
2. Remove user-facing calls to generated helpers like `__api_endpoint_greet()`.
3. Make the mounted `ApiRouter` tree the source of exported endpoints.
4. Preserve axum features: state, layers, route layers, nesting, merging,
   fallback handlers, route services, and ordinary extractors.
5. Make endpoint rename mostly a normal Rust rename plus cross-language API
   edits.
6. Show `Usage count: 0` for fresh-but-unused symbols instead of `pending`.
7. Keep hover, references, rename, and diagnostics useful for unsaved buffers.

## Non-goals

1. Do not build a new web framework.
2. Do not edit generated TypeScript or generated Rust glue during rename.
3. Do not require the TypeScript generated package to be regenerated on every
   keystroke.
4. Do not infer exported endpoints from every public `#[api]` item. The router
   tree remains the explicit publication boundary.

## Public API Design

### Endpoint Declaration

`#[api]` stays on the real Rust handler. It continues to validate endpoint
shape and produce endpoint metadata. It additionally generates a hidden axum
adapter.

Input:

```rust
#[api_macros::api(method = "POST", path = "/users")]
pub async fn create_user(
    request: Body<CreateUserRequest>,
) -> Result<Created<User>, UserError> {
    todo!()
}
```

Generated hidden items:

```rust
#[doc(hidden)]
pub fn __api_endpoint_descriptor_create_user() -> api_core::EndpointDescriptor {
    ...
}

#[doc(hidden)]
pub async fn __api_axum_handler_create_user(
    request: Body<CreateUserRequest>,
) -> axum::response::Response {
    api_axum::success_or_error(create_user(request).await)
}
```

For non-`Result` endpoints, the generated handler returns
`IntoResponse::into_response(endpoint_call.await)`.

For non-async SSE endpoints, the generated handler is async but calls the
endpoint without `.await`.

### Router Declaration

Add `#[api_macros::api_router]` for functions that construct API route trees.
The function body is normal Rust with a small declarative extension:

```rust
#[api_macros::api_router]
pub fn routes() -> api_axum::ApiRouter<AppState> {
    api_axum::ApiRouter::new("server")
        .endpoint(get_user)
        .endpoint(create_user)
        .nest("/admin", admin::routes())
        .route("/healthz", axum::routing::get(healthz))
        .route_layer(auth_layer())
        .with_state(AppState::new())
}
```

The macro rewrites:

```rust
.endpoint(get_user)
```

into:

```rust
.endpoint_descriptor(
    __api_endpoint_descriptor_get_user(),
    __api_axum_handler_get_user,
    api_core::SourceRange::from_macro_call(...)
)
```

The exact generated name is hidden and considered unstable. The LSP records
the source range of `get_user` inside `.endpoint(get_user)` as the router mount
reference.

### Router Runtime

Extend `api_axum::ApiRouter<S>` so it owns:

```rust
pub struct ApiRouter<S = ()> {
    module_name: String,
    router: axum::Router<S>,
    tree: api_core::ApiRouteTree,
}
```

Important methods:

```rust
impl ApiRouter<()> {
    pub fn new(name: impl Into<String>) -> Self;
    pub fn from_module(module: ApiModule) -> Self; // compatibility
}

impl<S> ApiRouter<S>
where
    S: Clone + Send + Sync + 'static,
{
    pub fn endpoint_descriptor<H, T>(
        self,
        descriptor: EndpointDescriptor,
        handler: H,
        source: SourceRange,
    ) -> Self
    where
        H: axum::handler::Handler<T, S>,
        T: 'static;

    pub fn route(self, path: &str, method_router: axum::routing::MethodRouter<S>) -> Self;
    pub fn route_service<T>(self, path: &str, service: T) -> Self;
    pub fn nest(self, path: &str, router: ApiRouter<S>) -> Self;
    pub fn merge(self, router: ApiRouter<S>) -> Self;
    pub fn layer<L>(self, layer: L) -> Self;
    pub fn route_layer<L>(self, layer: L) -> Self;
    pub fn fallback<H, T>(self, handler: H) -> Self;
    pub fn with_state<S2>(self, state: S) -> ApiRouter<S2>;
    pub fn into_router(self) -> axum::Router<S>;
    pub fn into_api_module(self) -> ApiModule;
    pub fn into_route_tree(self) -> ApiRouteTree;
}
```

`route`, `route_service`, and `fallback` are axum pass-throughs and are not
exported to TypeScript unless they explicitly mount an API endpoint. They still
stay in the route tree as opaque runtime nodes so source maps and diagnostics
can explain the final router shape.

### Route Tree

Add a first-class route tree to `api-core`:

```rust
pub struct ApiRouteTree {
    pub module_name: String,
    pub nodes: Vec<ApiRouteNode>,
}

pub enum ApiRouteNode {
    Endpoint(MountedEndpoint),
    Nest {
        path: String,
        source: SourceRange,
        child: Box<ApiRouteTree>,
    },
    Merge {
        source: SourceRange,
        child: Box<ApiRouteTree>,
    },
    Layer {
        source: SourceRange,
        child_count: usize,
    },
    RouteLayer {
        source: SourceRange,
        child_count: usize,
    },
    RawRoute {
        path: String,
        source: SourceRange,
    },
    RawService {
        path: String,
        source: SourceRange,
    },
    Fallback {
        source: SourceRange,
    },
}

pub struct MountedEndpoint {
    pub descriptor: EndpointDescriptor,
    pub source: SourceRange,
    pub effective_method: HttpMethod,
    pub effective_path: String,
}
```

The collector flattens `ApiRouteTree` into `ApiModule` and `ApiContract`.
`nest("/api", child)` prefixes the effective contract paths for endpoints
inside `child`, matching axum runtime behavior. If a user intentionally wants
runtime and contract paths to diverge, keep `route_override` as an explicit
legacy/escape-hatch API.

## Extractor And Response Model

### Existing Contract Extractors

Continue supporting:

- `api_axum::Path<T>`
- `api_axum::Query<T>`
- `api_axum::Body<T>`
- `api_axum::Binary<T>`

These participate in the TypeScript contract.

### Server-only Extractors

Support server-only axum extractors incrementally:

- `axum::extract::State<T>`
- `Extension<T>`
- headers and typed headers
- cookies
- custom `FromRequestParts` extractors

Server-only extractors are passed through to axum but not exported into the
TypeScript request shape.

The `#[api]` parser should classify every argument:

```rust
enum EndpointInputKind {
    ContractPath,
    ContractQuery,
    ContractBody,
    ContractBinaryBody,
    ServerOnlyParts,
    ServerOnlyBody,
}
```

Rules:

1. Contract body and server-only body extractors cannot both appear.
2. A body extractor must remain last, following axum's extraction rules.
3. Unknown extractors default to server-only parts only if they implement
   `FromRequestParts`; otherwise rustc should produce the normal axum handler
   error.
4. A future explicit attribute can override classification:

```rust
#[api(server_only)]
state: State<AppState>
```

### Response Conversion

Keep response conversion macro-generated to avoid trait-overlap problems.

`#[api]` already parses return type shape. Use that parse result to choose the
adapter expression:

- `Result<T, E>`: `api_axum::success_or_error(endpoint_call)`
- plain `T`: `axum::response::IntoResponse::into_response(endpoint_call)`
- SSE `Result<Sse<T, Stream>, E>`: same `success_or_error`
- SSE plain `Sse<T, Stream>`: plain `IntoResponse`

## Collector And Symbol Graph Changes

### Contract Collection

Add `CollectorInput::from_root`:

```rust
impl CollectorInput {
    pub fn from_root<R>(
        package_name: impl Into<String>,
        root: R,
    ) -> Self
    where
        R: api_core::IntoApiRoot;
}
```

Internally this calls `root.into_api_module()` and preserves route-tree source
metadata when the root also exposes a route tree.

Update the temporary collector crate generation in
`crates/api-collector/src/main.rs` so the configured `api_root` may return
either:

- `api_core::ApiModule`
- `api_axum::ApiRouter`
- `api_core::ApiRouteTree`

Use a small trait in `api-core`:

```rust
pub trait IntoApiRoot {
    fn into_api_module(self) -> ApiModule;
    fn into_route_tree(self) -> Option<ApiRouteTree>;
}
```

### Graph Schema

Move the graph toward a relationship model:

```rust
Symbol {
  id
  kind
  names: { rust, typescript, wire }
  usage: {
    status: "fresh" | "live" | "stale" | "missing" | "running" | "untracked"
    count: number | null
    reads?: number
    writes?: number
  }
  locations: Location[]
}

Location {
  role:
    | "rustDeclaration"
    | "rustReference"
    | "rustRouterMount"
    | "rustRoutePath"
    | "rustSerdeAttribute"
    | "typescriptUsage"
    | "generatedDefinition"
  language: "rust" | "typescript"
  generated: boolean
  renamable: boolean
  renameStrategy:
    | "rustAnalyzer"
    | "literal"
    | "rustIdent"
    | "tsAccessor"
    | "routePlaceholder"
    | "serdeRename"
  range
  nameRange
}
```

Compatibility: `api-ls` should read the current v1 shape and normalize it to
the new in-memory model before answering requests.

### Router Source Locations

Record these locations for each endpoint:

- `rustDeclaration`: `fn greet`
- `rustRouterMount`: `.endpoint(greet)`
- `generatedDefinition`: generated TypeScript accessor
- `typescriptUsage`: `greetings.greet` in user TS files

Legacy mode should also record:

- `api_module!(..., endpoints = [greet])`
- `__api_endpoint_greet()`
- `__api_endpoint_descriptor_greet()`

Those legacy locations can be removed after examples and docs migrate.

## Usage Count Fix

### Current Bug

`requested_name` shows `Usage count: pending` because:

1. `SymbolGraph::load_enriched` sets `metadata.usage_count` only for endpoint
   symbols.
2. Field usage data exists in `field_usages`, but hover does not translate a
   fresh index with zero field usages into `0`.
3. Usage locations written into the graph are marked `renamable: false`.
4. `pending` currently conflates missing, stale, and fresh-zero usage states.

### Required Behavior

Hover should use this matrix:

| Usage state | Hover text |
| --- | --- |
| Fresh/live index, symbol has N usages | `Usage count: N` |
| Fresh/live index, symbol has no usages | `Usage count: 0` |
| Usage scan running for current snapshot | `Usage count: pending` |
| Usage index missing | `Usage count: pending` |
| Usage index stale for graph | `Usage count: pending` |
| Symbol kind not tracked | omit usage line or show `Usage: untracked` |

`pending` is reserved for unknown status, not for zero.

### Implementation Steps

1. Add `UsageSummary` to `api-ls`'s normalized graph model:

   ```rust
   struct UsageSummary {
       status: UsageStatus,
       count: Option<u64>,
       reads: Option<u64>,
       writes: Option<u64>,
   }
   ```

2. Extend `EffectUsageIndex` or derive summaries from existing arrays:

   - endpoints: strong usage count from `endpoints[].strong`
   - fields: count/read/write from `field_usages`
   - route params: count/read/write from `field_usages`
   - query params: count/read/write from `field_usages`
   - error variants/tags/fields: count from `error_usages` and `field_usages`

3. Change `SymbolGraph::load_enriched`:

   - if index is fresh, set `UsageSummary { status: Fresh, count: Some(0) }`
     for every tracked symbol before adding locations.
   - update counts as locations are added.
   - never leave a tracked symbol at `None` when the index is fresh.

4. Change `update_symbol_graph_usage_locations` in the collector:

   - write usage counts for all usage-enriched symbol kinds, not only
     endpoints.
   - mark user TypeScript usage locations as `renamable: true`.
   - set `renameStrategy: "tsAccessor"` where appropriate.

5. Add tests:

   - fresh index with no `field_usages` makes `requested_name` hover show
     `Usage count: 0`.
   - missing usage index still shows `pending`.
   - stale usage index still shows `pending`.
   - endpoint hover still counts only strong endpoint usage.
   - field hover can display read/write detail once read/write counts are
     available.

## Rename Plan

### Current Bug

Renaming the Rust endpoint function with LSP does not update all API-related
places because:

1. `api-ls` handles API rename from the graph alone.
2. Rename uses `SymbolGraph::load`, not `load_enriched`.
3. It does not ask rust-analyzer for ordinary Rust rename edits.
4. TypeScript usage locations are not renamable.
5. User-visible generated helper calls exist and are not first-class API graph
   locations.
6. Unsaved file contents are not included in the graph used by rename.

### Target Behavior

Renaming `greet` to `salute` from Rust should update:

- `pub async fn greet` to `pub async fn salute`
- `.endpoint(greet)` to `.endpoint(salute)`
- ordinary Rust references such as `greet(name).await`
- TypeScript usages such as `greetings.greet` to `greetings.salute`
- generated TypeScript on next generation only, not through direct edit

In legacy mode, it should also update:

- `api_module!(..., endpoints = [greet])`
- `__api_endpoint_greet()`
- `__api_endpoint_descriptor_greet()`
- `greet_response` only if it is semantically tied to the endpoint and can be
  renamed safely; otherwise leave it alone or remove it during migration

Renaming from TypeScript should apply the same identity change in reverse:

- `greetings.greet` to `greetings.salute`
- Rust declaration to `salute`
- Rust router mount/reference locations to `salute`
- generated files are not edited

### Rename Orchestrator

Replace graph-only rename with a multi-source orchestrator inside `api-ls`.

Flow:

1. Resolve the symbol at the requested position using the live normalized graph.
2. Validate the target name against the symbol kind:

   - endpoint/type/field Rust name: Rust identifier rules
   - TypeScript accessor: TypeScript identifier rules
   - wire field/tag/route param: wire identifier rules

3. Compute name variants:

   ```rust
   struct RenameTexts {
       rust: String,
       typescript: String,
       wire: String,
       route_placeholder: Option<String>,
   }
   ```

4. If the rename touches a Rust declaration or Rust reference, forward
   `textDocument/rename` to rust-analyzer with the Rust name.
5. If the rename starts from TypeScript, still ask rust-analyzer to rename the
   Rust declaration by issuing a backend rename at the Rust declaration
   location.
6. Build API graph edits:

   - user TypeScript accessor usages
   - route placeholders inside `#[api(path = "...")]`
   - `serde(rename = "...")` insert/update/remove edits
   - legacy helper calls until migration is complete

7. Optionally ask the TypeScript backend for rename only for non-generated
   ordinary TS symbols. Do not use it to edit generated package files.
8. Merge all edits into one `WorkspaceEdit`.
9. Return a clear error if edits overlap with different replacement text.

### Backend Request Handling

Rename currently returns synchronously when `api-ls` owns the request. The new
orchestrator needs async backend requests.

Add a pending request kind:

```rust
PendingRequestKind::ApiRename {
    client_id: Value,
    request_id: String,
    symbol_id: String,
    new_name: String,
    api_edits: WorkspaceEditAccumulator,
    waiting_for: usize,
}
```

When backend rename responses arrive:

1. Normalize their `WorkspaceEdit`.
2. Add edits to the accumulator.
3. Decrement `waiting_for`.
4. When all responses are received, run overlap detection and reply to the
   client.

If a backend fails:

- fail the rename if rust-analyzer failed for a Rust-side rename.
- ignore TypeScript backend failure if API graph edits already cover user TS
  accessor usages.

### Edit Merge Rules

All rename sources write into a single accumulator:

```rust
struct TextEditKey {
    uri: String,
    range: GraphRange,
}
```

Rules:

1. Exact duplicate edit: keep one.
2. Same range, same text: keep one.
3. Same range, different text: fail.
4. Overlapping ranges: fail unless one edit fully contains the other and both
   replacement texts are identical after applying inner edits.
5. Generated file edit: reject unless explicitly marked as generated cache
   maintenance outside LSP rename.
6. Dirty open document: use versioned `TextDocumentEdit` when the client
   supplied a version.

### Rename Tests

Add tests for:

1. Rust endpoint rename in the new `.endpoint(greet)` style.
2. TypeScript endpoint accessor rename back to Rust.
3. Route param rename updates:

   - Rust argument
   - `#[api(path = "/.../{param}")]`
   - TypeScript request object properties

4. Field rename updates:

   - Rust field
   - serde rename attribute if required
   - TypeScript reads/writes

5. Generated package files are never edited.
6. Legacy `api_module!` endpoint list is renamed until migration removes it.
7. Overlapping edits fail safely.
8. Unsaved `.endpoint(greet)` change is included in rename edits.

## Live LSP Synchronization Plan

### Current Problem

`api-ls` is an LSP gateway. It forwards `didOpen`, `didChange`, and `didSave`
to rust-analyzer and TypeScript, but its own cross-language graph is loaded
from disk artifacts:

- `target/api-contract/rust-ts-symbols.json`
- `target/api-contract/graph/effect-usage-index.json`

That means cross-language hover, definition, references, rename, and unused
diagnostics can lag behind unsaved editor state.

### Desired Model

`api-ls` should answer from the best available snapshot:

1. Live open-buffer overlay.
2. Fresh disk graph/index.
3. Stale disk graph/index with reduced confidence.
4. Backend-only fallback.

The LSP must never pretend stale data is fresh. It should degrade gracefully:

- navigation can still use stable symbol IDs when possible.
- hover can say `pending` only when usage is unknown.
- rename should include dirty buffers when it can prove ranges.
- diagnostics should not report unused endpoints from stale usage data.

### Document Store

Add an in-memory document store to `api-ls`:

```rust
struct OpenDocument {
    uri: String,
    path: PathBuf,
    language_id: Option<String>,
    version: Option<i64>,
    text: String,
    dirty: bool,
}

struct DocumentStore {
    documents: BTreeMap<String, OpenDocument>,
}
```

Handle:

- `textDocument/didOpen`: store full text and version.
- `textDocument/didChange`: apply full or incremental changes, update version,
  mark dirty.
- `textDocument/didSave`: update text if provided, mark clean, schedule saved
  artifact refresh.
- `textDocument/didClose`: remove overlay and fall back to disk.
- `workspace/didChangeWatchedFiles`: invalidate disk graph/index cache.

Continue forwarding all notifications to rust-analyzer and TypeScript.

### Live Graph Service

Add:

```rust
struct GraphService {
    disk_graph: Option<CachedGraph>,
    disk_usage_index: Option<CachedUsageIndex>,
    live_graph: Option<VersionedGraph>,
    live_usage_index: Option<VersionedUsageIndex>,
    running_jobs: BTreeMap<JobId, GraphJob>,
}
```

Responsibilities:

1. Load disk artifacts lazily and cache by file mtime/hash.
2. Merge disk graph with open-buffer overlays.
3. Track usage status per symbol.
4. Schedule background rebuilds.
5. Discard stale job results using snapshot IDs.

### Rust Dirty Buffer Overlay

Compiler-backed collection still requires saved files. For unsaved buffers,
use a tolerant syntactic overlay.

Implementation options:

1. Preferred: add `ra_ap_syntax` to `api-ls` for tolerant Rust parsing.
2. Fallback: use `syn` for complete items and keep disk ranges when parsing
   fails.

The overlay parser should extract:

- `#[api(...)]` endpoint function names and source ranges.
- endpoint route path string ranges.
- endpoint argument names and wrapper kinds.
- `#[api_router]` functions.
- `.endpoint(handler)` source ranges.
- legacy `api_module!(..., endpoints = [...])` ranges.
- legacy generated helper call ranges.
- serde field rename attributes near API fields.

The overlay does not need to rebuild the entire contract on every keystroke.
It needs enough structure for:

- hover identity
- references
- rename ranges
- usage freshness decisions

When parsing fails, keep previous live overlay for that document only if the
current edit did not touch the relevant range. Otherwise mark affected symbols
as `running` or `stale`.

### TypeScript Dirty Buffer Overlay

The semantic usage scanner already accepts in-memory TypeScript source files.
Update `api-ls` to pass a mixed snapshot:

- open TypeScript documents from `DocumentStore`
- saved TypeScript files from disk for unopened files
- generated package declarations from the generated cache

Schedule a debounce:

- immediate invalidation on change
- scan after 150 to 300 ms of quiet time
- cancel/discard older scan results using snapshot IDs

The live usage index should include:

- endpoint usages
- error usages
- field usages
- read/write classification
- diagnostics from the TypeScript backend where available

If TypeScript is syntactically broken, keep the previous live index but mark
changed files as stale. Hover should show `pending` for symbols whose counts
depend on those files.

### Snapshot Freshness

Introduce snapshot IDs:

```rust
struct SnapshotId {
    disk_contract_hash: String,
    open_document_versions: BTreeMap<String, i64>,
}
```

Every live graph and live usage index records the snapshot it was built from.

Freshness rules:

1. Live graph and live usage index with same snapshot: `live`.
2. Disk graph and disk usage index with matching contract hash and no relevant
   dirty documents: `fresh`.
3. Graph exists but usage index hash does not match: `stale`.
4. Usage job scheduled but not complete: `running`.
5. No usage index exists: `missing`.

Hover uses these states. Diagnostics only use `fresh` or `live`.

### File Save Flow

On Rust save:

1. Mark document clean.
2. Forward save to rust-analyzer.
3. Schedule background `api check` or a lighter `api collect + gen graph`
   command for the package.
4. Reload disk graph when the generated graph file changes.
5. Keep live overlay active until the disk graph catches up.

On TypeScript save:

1. Mark document clean.
2. Forward save to TypeScript.
3. Re-run semantic usage scan with current open buffers and saved files.
4. Write disk usage index only from explicit `api check`, `api watch`, or a
   configured LSP background write mode. The default LSP live index can remain
   in memory.

### Diagnostics

Unused endpoint diagnostics should be published only when:

- the endpoint is exported in the current live or fresh route tree.
- usage status is `fresh` or `live`.
- the endpoint is not `allow_unused`.

Clear diagnostics when:

- the graph becomes stale.
- the endpoint is removed from the live route tree.
- the usage scanner is running and previous diagnostics may be invalid.

## Risks And Mitigations

### Macro Rewriting Method Chains

Risk: `#[api_router]` rewriting chained calls could become brittle.

Mitigation:

- Support only simple `.endpoint(path::to::handler)` at first.
- Emit precise compile errors for unsupported forms.
- Keep `endpoint_descriptor` as an explicit escape hatch for advanced cases.

### Unsaved Rust Contract Accuracy

Risk: unsaved Rust may not compile, so a full contract cannot be collected.

Mitigation:

- Use tolerant syntax overlays for identity/range-level features.
- Keep full type/contract changes pending until save.
- Never publish contract diagnostics from incomplete overlays.

### Rename Conflicts

Risk: rust-analyzer and API graph edits may overlap.

Mitigation:

- Centralize edit merge logic.
- Reject conflicting overlaps.
- Prefer rust-analyzer for ordinary Rust identifiers.
- Prefer API graph edits for TypeScript API accessors and wire strings.

### Performance

Risk: scanning TypeScript on every keystroke could be expensive.

Mitigation:

- Debounce scans.
- Scan only affected TS project roots.
- Reuse generated package metadata.
- Discard stale job results.
- Keep hover responsive by using previous index with `running` status.

## Definition Of Done

The architecture is complete when:

1. A new axum server can define `#[api]` handlers and mount them with
   `.endpoint(handler)`.
2. No user code needs `greet_response`.
3. No user code needs `__api_endpoint_greet()`.
4. Contract collection can start from the declarative router tree.
5. Hover on a fresh unused field shows `Usage count: 0`.
6. Rename from Rust and TypeScript updates Rust source and user TypeScript
   usages without editing generated files.
7. Unsaved TypeScript usage changes are reflected in hover/references after a
   short debounce.
8. Unsaved Rust router edits are reflected in references/rename when syntactic
   parsing succeeds.
9. Stale usage data never produces false unused endpoint diagnostics.
10. Existing legacy APIs continue to work during migration.
